# Workspace Wiki 需求说明

状态：第 5 期已完成。通知、权限收尾和权限回归已经接入。

## 1. 背景

Workspace 需要一套知识库，用来管理多级目录下的文本文档。阅读、编辑、版本和编辑器体验与现有 Project Pages 保持一致。Wiki 与 Pages 的差别只有三处：挂在 Workspace 而不是 Project、目录和文件可以按成员授权、非创建者的修改必须经过创建者审阅后才能进入正文。

## 2. 目标

- 成员能在 Workspace 内按多级目录组织 Wiki 文档。
- 创建者能把某个目录或文件对指定成员设为不可见、可见或可编辑。
- 非创建者的修改先形成变更请求，创建者审阅通过后才写入正文。
- 正文在审阅期间被创建者改过时，合并前可以解决冲突。
- 权限和审阅之外，文档能力与 Pages 一致。

## 3. 不在本次范围

- 不替换、不迁移现有 Project Pages。
- 不把 Wiki 挂到 Project 下，也不把一篇 Wiki 文档关联到多个 Project。
- 不做跨 Workspace 分享，不做公开互联网链接。
- 不把审阅流程做成通用审批流，审批人固定为该文件的创建者。
- 不支持把创建者身份转给其他人。第一版创建者不可变更。

## 4. 角色

| 角色             | 说明                                                                    |
| ---------------- | ----------------------------------------------------------------------- |
| Workspace 管理员 | 可以进入 Wiki。对具体目录和文件没有额外权限，除非自己是创建者或被授权。 |
| Workspace 成员   | 可以创建目录和文件。对其余节点只拥有被授予的权限。                      |
| 节点创建者       | 创建该目录或文件的人。始终可以看见、编辑、授权和删除自己创建的节点。    |
| 被授权成员       | 被创建者授予不可见、可见或可编辑的人。                                  |
| Guest            | 默认不能进入 Wiki，也不能被授权。                                       |

创建者编辑的是已发布正文，保存后立即生效。其他成员即使被授予可编辑，也不能直接改正文。

## 5. 概念

| 术语       | 含义                                                           |
| ---------- | -------------------------------------------------------------- |
| 目录       | 只用来组织结构，本身没有正文。                                 |
| 文件       | 一篇 Wiki 文档，正文形态与 Page 相同。                         |
| 节点       | 目录或文件。                                                   |
| 已发布正文 | 当前对外生效的文件内容。                                       |
| 变更请求   | 非创建者基于某一版已发布正文提交的修改，审阅通过前不影响正文。 |
| 基线版本   | 创建变更请求时对应的已发布版本。                               |

目录和文件都有独立的创建者。子文件的创建者不是父目录的创建者，除非是同一个人。

## 6. 信息架构

Wiki 入口在 Workspace 侧边栏，路由归属 Workspace，不出现在 Project 内。

根目录由系统为每个 Workspace 预置，名称为 Wiki。根目录没有个人创建者，Workspace 内的管理员和成员都能看见。任何管理员或成员都可以在自己有权新增子节点的目录下创建子目录和文件。

目录可以无限嵌套。文件只能放在目录下，文件下面不能再挂文件或目录。同一目录内的名称允许重复。节点可以在创建者有权操作的范围内移动和排序。

删除规则：

- 只有该节点的创建者可以删除它。
- 目录下仍有别人创建的子节点时，不能删除该目录。
- 删除目录会同时删除该创建者名下、且不再包含他人节点的全部子孙。
- 删除为软删除，与 Pages 一致，可恢复。

## 7. 权限

### 7.1 权限级别

| 级别   | 目录                                               | 文件                                                     |
| ------ | -------------------------------------------------- | -------------------------------------------------------- |
| 不可见 | 目录及其整棵子树对该成员隐藏。                     | 文件对该成员隐藏，不能从搜索、最近访问、链接和提及打开。 |
| 可见   | 能看到目录和有权看到的子节点，不能在该目录下新建。 | 能阅读已发布正文，不能发起变更请求。                     |
| 可编辑 | 能在该目录下新建子目录和文件。                     | 能基于已发布正文发起变更请求，不能直接修改已发布正文。   |

不可见不是一条普通授权，而是显式拒绝。它优先于从父节点继承来的可见和可编辑。

### 7.2 谁可以改权限

只有该节点的创建者可以修改它的权限，也只有创建者可以删除它。父目录的创建者不能改子节点的权限，也不能删别人创建的子节点。

创建者不能把自己设为不可见，也不能移除自己的权限。根目录不能设置成员权限。

### 7.3 继承与覆盖

成员对某个节点的有效权限按下面的顺序决定：

1. 该成员是节点创建者：可编辑，并额外拥有授权和删除权。
2. 该节点上存在针对该成员的显式权限：使用显式权限。
3. 否则沿父目录向上，使用最近一条显式权限。
4. 直到根目录仍没有显式权限：不可见。

补充约束：

- 任一祖先目录对该成员是不可见时，该成员看不到这棵子树，子节点上更宽松的授权不生效。
- 父目录是可见时，子节点可以把同一个人降为不可见，或保持可见。子节点不能把只拥有可见权限的人提升为可编辑。
- 父目录是可编辑时，子节点可以维持可编辑，或降为可见、不可见。
- 新建节点默认不添加任何显式授权，因此除创建者外，其他成员不可见。创建者可以在创建时或创建后授权。

没有权限查看某节点的人，不能通过直接输入地址打开它。接口返回与资源不存在相同的结果，不透露节点是否存在。

### 7.4 权限变更的即时影响

- 改为不可见后，该成员立即失去入口；正在阅读的页面下次请求失败。
- 从可编辑降为可见后，不能再新建变更请求。已经打开的变更请求仍可由创建者审阅，提交人不能再更新它。
- 取消目录的可编辑后，不能在该目录下新建节点，已创建的子节点保留。

## 8. 编辑与审阅

### 8.1 创建者

创建者修改已发布正文时直接保存，立即生效，并写入版本历史。不需要给自己提变更请求。

创建者使用与 Pages 相同的编辑器和协同保存方式。协同范围只包括创建者自己的会话，其他成员不能加入已发布正文的协同编辑。

### 8.2 可编辑成员

可编辑成员要修改文件时，必须创建变更请求：

1. 以当前已发布正文为基线复制一份草案。
2. 只在草案上编辑。草案可以使用与 Pages 相同的编辑器。
3. 提交给该文件的创建者。
4. 创建者通过并合并后，变更写入已发布正文，并产生一个新的已发布版本。

同一文件、同一提交人同时只能有一个未关闭的变更请求。已有开放请求时，继续修改会更新这份请求，而不是再开一份。

可见成员只能阅读已发布正文。不可见成员不能感知该文件。

### 8.3 变更请求状态

| 状态   | 含义                                       | 可执行的操作                             |
| ------ | ------------------------------------------ | ---------------------------------------- |
| 草稿   | 提交人正在编辑，创建者还不能合并。         | 提交人可编辑、提交或关闭。               |
| 待审阅 | 已提交，等待创建者处理。                   | 创建者可通过、退回或关闭。提交人可关闭。 |
| 需修改 | 创建者退回并留下意见。                     | 提交人可继续编辑后再次提交，或关闭。     |
| 冲突   | 基线已落后于当前已发布正文，不能直接合并。 | 创建者解决冲突后合并，或退回给提交人。   |
| 已合并 | 已写入正文。                               | 只读。                                   |
| 已关闭 | 未写入正文。                               | 只读。                                   |

创建者是唯一审批人。不能加签，不能改派。

### 8.4 合并

合并前系统比较变更请求的基线版本和当前已发布版本：

- 基线仍是当前已发布版本：按变更请求的内容直接成为新的已发布正文。
- 基线已经过期，但双方修改的内容块没有重叠：自动合并，生成新的已发布版本。
- 同一内容块双方都改过：进入冲突状态，必须人工解决后才能合并。

自动合并和人工解决的结果都记为一次由创建者完成的发布。版本历史中保留变更请求的链接。

### 8.5 冲突解决

冲突按编辑器的内容块比较，不按纯文本行比较。界面分成三栏：

- 基线：提交人开草案时的已发布正文。
- 当前正文：创建者之后已经发布的内容。
- 提交内容：变更请求中的草案。

每个冲突块可以选择保留当前正文、采用提交内容，或手工编辑成合并结果。非冲突块按自动合并结果展示，创建者仍可以改。创建者确认后，合并结果成为新的已发布正文，变更请求变为已合并。

创建者也可以不在这里改，把请求退回给提交人。提交人只能改自己的草案；退回不会把当前正文交给提交人编辑。

冲突没有解决前，不能部分合并。

### 8.6 并发

- 创建者发布新版本时，不自动改写其他开放草案的内容，只把对应请求标为可能冲突。
- 同一变更请求只允许提交人编辑草案。
- 两个可编辑成员各自拥有自己的变更请求，互不覆盖。
- 合并顺序以创建者实际合并的顺序为准。后合并的请求如果碰到来自前一次合并的冲突，必须先解决。

## 9. 与 Pages 保持一致的能力

以下能力作用在 Wiki 文件的已发布正文上，交互和数据形态与 Pages 一致：

- 富文本正文，包含现有 Pages 支持的块、提及、嵌入和附件。
- 标题、图标、颜色、宽屏等展示属性。
- 版本历史、查看历史版本、恢复历史版本。恢复只影响已发布正文，不改写开放的变更请求。
- 锁定、解锁、归档、取消归档、复制。
- 复制文件时，新文件的创建者是执行复制的人，正文成为新的已发布正文，不复制原权限和开放的变更请求。
- 工作区内搜索已发布正文。搜索结果必须先过权限。
- 最近访问。
- 收藏。
- 软删除与恢复。

目录只继承组织能力：名称、图标、排序、移动、归档和软删除。目录没有正文、版本历史和变更请求。

锁定后的文件，创建者和其他成员都不能改已发布正文，也不能新建变更请求，直到创建者解锁。

## 10. 通知

以下事件通知对应的人：

| 事件                   | 接收人                     |
| ---------------------- | -------------------------- |
| 变更请求被提交         | 文件创建者                 |
| 变更请求被退回         | 提交人                     |
| 变更请求被合并或关闭   | 提交人                     |
| 节点权限被授予或变更   | 被授权的成员               |
| 文件被创建者锁定或归档 | 该文件开放变更请求的提交人 |

不可见的成员不接收该节点的任何通知。

## 11. 开发计划

按依赖顺序分五期。前一期的验收完成后再开始下一期。

### 第 1 期：目录与权限

- Workspace 入口、根目录、多级目录和文件节点。
- 创建、重命名、移动、排序、软删除和恢复。
- 成员级不可见、可见、可编辑，以及继承、覆盖和祖先不可见优先。
- 只有创建者可以授权和删除。

验收：未被授权的成员看不到节点，也不能通过地址打开；创建者可以逐个成员授权；子节点不能绕过父目录的不可见。

### 第 2 期：正文与 Pages 基础能力

- 复用 Pages 编辑器保存已发布正文。
- 创建者直接编辑并产生版本历史。
- 可见成员只读。
- 标题、图标、颜色、宽屏、锁定、归档、复制、搜索、最近访问和收藏。

验收：创建者的修改立即可见；可见成员不能保存正文；版本可以查看和恢复。

### 第 3 期：变更请求

- 可编辑成员创建草案、提交、撤回和关闭。
- 创建者通过、退回和合并。
- 同一提交人对同一文件只有一个开放请求。
- 无冲突时合并后正文和版本历史更新。

验收：可编辑成员的保存不会改变已发布正文；创建者合并后，正文变为提交内容。

### 第 4 期：冲突

- 检测过期基线和重叠内容块。
- 不重叠的修改自动合并。
- 三栏冲突解决界面。
- 未解决冲突时不能合并。

验收：创建者在变更请求打开后修改同一块内容，合并被拦住；创建者逐块选择或手工编辑后，正文得到预期结果。

### 第 5 期：通知与收尾

- 第 10 节的通知。
- 权限变化对正在阅读和正在审阅的影响。
- 搜索、最近访问、收藏和复制的权限回归。

验收：不可见成员收不到内容通知；降为可见后不能再更新草案。

## 12. 已确定的产品规则

- 创建者改正文，直接生效。
- 其他可编辑成员只能提交变更请求。
- 新节点默认只有创建者可见。
- 没有显式权限时不可见，不向全体成员公开。
- Guest 不能使用 Wiki。
- 同一人同一文件只有一个开放变更请求。
- 冲突按内容块处理。
- 创建者不可转让。
