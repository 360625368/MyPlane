1 · 它是什么

《文件索引》是 G-Choco Quant 全部文档、工具、程序、网页的目录与唯一入口，也是各部分负责人、各文件维护人的唯一出处（《G-Choco Quant 运营机制》0.5）。它不存文件内容，只存：条目在树里的位置、名称与说明、维护人、权限标签、入口（网址或上传文件）。

页面是一张树形表格：每行一个条目（文件夹或文件），左侧是自动生成的编号，可展开折叠、搜索筛选、拖拽移动；有编辑权限的人可新建、改名、移动、删除、改入口、上传。

2 · 数据模型

2.1 条目 items（每个条目一条记录，主键 uid）

字段 类型 含义与规则
uid string 主键，生成后永不改变。格式不限（现行为 u + 时间 + 随机串）；编号变化不影响它
parent string 父条目的 uid；顶层为 ""
order number 同一父条目下的排序键。每次结构操作后重排为连续整数：顶层 0,1,2…；其他层 1,2,3…（见 2.6）。插入时可临时取 ±0.5、1e9、-1 等，重排后归整
kind "folder" / "file" 类型。有子条目的一律视为文件夹（不论 kind）
name string 名称，必填
desc string 说明
owner string 文件：维护人；文件夹：负责人。现为人名文本（如 Eric），迁移后改为用户 ID 引用，显示时解析为人名
access "团队内" / "工段" / "机密" / "—" / "" 权限标签。文件夹不显示。机密 触发入口隐藏（第 4 节）
freq string 更新频率（如「每周」「改动时」）。现行页面不作为列显示（代码里过滤掉了），但数据保留，迁移时保留字段
url string 入口网址，须以 http:// 或 https:// 开头；与 asset 互斥
asset string 上传文件的资产 ID；与 url 互斥
assetName string 上传时的原文件名，显示用
leaders string[] 只在第二层（编号 n.n）文件夹上有意义：该部门的负责人用户 ID 列表（编辑授权，见第 4 节）
viewers string[] 只在 access=机密 的文件上有意义：被单独授权看到入口的用户 ID 列表
ownerOnly boolean 只在顶层文件夹上有意义：true 时该文件夹及全部子孙只对所有者（JT）可见
trashed boolean 在回收站中
trashedAt ISO 时间 进回收站的时间
trashedFrom string 进回收站时的父 uid，用于恢复
c<时间戳> string 用户自建列的值（键名见 meta.columns）。当前数据中没有自建列

2.2 元数据 meta

  • columns.cols：可见列的定义与顺序，[{key,label}]。基础列固定为 name 名称 / desc 说明 / owner 维护人 / access 权限 / url 入口，不可删除；自建列键名形如 c1739...，可删除。
  • schema.v：数据结构版本，当前为 3。

2.3 访问记录 seen

键为用户 ID，值 {t: ISO 时间}。编辑者（非所有者）打开页面时写入（距上次超过 7 天才更新；查看者没有写权限，写入会静默失败）。用途：人员选择器里列出「打开过本页的成员」，弥补平台搜索搜不到外部受邀成员的问题。迁移后若新系统有完整的用户目录，可改为直接搜索用户目录，本集合可以废弃。

2.4 上传文件 assets

现行存在 Claude 平台的资产库，按 /_blob/<资产ID> 访问。允许的类型：.pdf .png .jpg .jpeg .gif .webp .md .json .csv .txt。当前只有 1 个文件（b1063547…，PDF），它所属的条目已在回收站。迁移时：文件存进对象存储，asset 字段改存新的文件 ID 或路径，assetName 保留。

2.5 每个人自己的浏览偏好（只存在本人浏览器，不进数据库，不需要审批）

键（localStorage） 内容
kb3_col 哪些文件夹是折叠的 {uid:true}
kb3_hc 隐藏的列 [key]
kb3_hr 隐藏的行 [uid]
kb3_flt 各列筛选条件
kb3_seeded 是否已做过「首次默认折叠」

2.6 派生规则（必须完全一致）

  1. 子条目：parent 等于该 uid、且不在回收站、且（当前用户是所有者或该条目不是 ownerOnly）的条目，按 order 升序、同值按 name 字典序。（kids()）
  2. 编号：从根开始深度优先。顶层从 0 起编（0, 1, 2…）；其余每层从 1 起（父编号.1, 父编号.2…）。编号不存储，每次渲染时由位置计算。（computeNums()）
  3. 是否文件夹：有子条目，或 kind=folder。（isFolder()）
  4. 是否在用：自身及所有祖先都不在回收站，且（对非所有者）没有 ownerOnly 祖先。（alive()）
  5. 所属部门文件夹：沿父链向上，找到「父条目是顶层」的那个条目，即第二层（编号 n.n）的祖先。（stageOf()）
  6. 第二层只放文件夹：任何操作若会让一个文件落在第二层（父条目是顶层），一律拒绝，弹出提示「第二层只放文件夹：编号 n.n 这一层只放文件夹，文件放在 n.n.n 或更深。请先在这里建一个文件夹，再把文件放进去。」适用于新建、升一级、降一级、移动到、拖拽。（l2file() / L2MSG()）
  7. 重排：每次结构操作后，对受影响的父条目把子条目的 order 重写为连续整数（顶层 0 起，其他 1 起）。（renorm()）

3 · 页面与交互（逐项）

3.1 页首

  • 标题「文件索引」，副标题「G-Choco Quant · 所有知识、工具、体系、规范、文件、代码、程序的编号与入口」，其后显示连接状态（已连接 / 未连接 / 读取失败）；非所有者额外显示「你的 ID：…」（便于所有者按 ID 授权）。
  • 工具条：搜索框（搜名称、说明、维护人、编号）；「全部展开」「全部折叠」「展开到第 2 层」。
  • 所有者额外看到：「↶ 撤销（n）」「＋ 顶层文件夹」「＋ 列」「回收站（n）」「导出 JSON」。部门负责人只看到「↶ 撤销」。
  • 状态提示区：显示当前身份说明，以及每次保存的结果（「保存中…」「✓ 已移动 · 时间」「保存失败 n 项：原因」）。
  • 「已隐藏」条：列出本人隐藏的列与行，可逐个恢复或「全部恢复」。
  • 计数条：无筛选时「共 N 项 · x 个文件 · y 个文件夹」；有筛选或搜索时「筛选结果 n 项 / 文件 a / 文件夹 b / 全库共 …」。

3.2 表格

  • 列：编号 + meta.columns 中未被本人隐藏的列 + 操作。表头吸顶。每个列头有「隐藏」；自建列另有「删除」（仅所有者）。
  • 表头第二行是筛选行：
    • 编号列：「清除筛选」按钮（无筛选时置灰）。
    • 名称列：类型下拉（全部 / 文件 / 文件夹）+ 文本「包含…」。
    • 说明列及自建列：文本「包含…」（不区分大小写）。
    • 维护人、权限、入口三列：多选弹层，选项为当前在用文件的去重值并显示计数，空值显示为「（空）」；入口列的选项固定为「网址 / 上传文件 / 暂无」，有机密时再加「机密」。弹层有「清除本列」。
    • 规则：维护人、权限、入口三列的筛选只匹配文件，文件夹在这三列有筛选时不算命中；命中条目的全部祖先也显示（半透明，表示只是路径）。
  • 行：
    • 缩进 12 + 层级×18 像素（层级最多按 4 计）；顶层行加底色、名称加粗加大、左侧色条；第二层名称加粗。
    • 编号列：所有者且无搜索无筛选时显示拖拽柄「⠿」；展开 / 折叠箭头（无子条目则占位隐藏）；编号徽章。
    • 名称列：📁 或 📄 + 名称（搜索命中处高亮）；文件夹后显示子条目数；ownerOnly 文件夹显示红色徽章「仅 JT 可见」。
    • 维护人：彩色胶囊（Eric 蓝、Yui 紫、CZ 绿、JT 橙、其他灰）；文件夹的这一列标题悬停为「负责人」。
    • 权限：胶囊（机密红、工段黄、团队内灰）；文件夹不显示。
    • 入口（文件夹不显示），四种状态：
      1. 当前用户看不到（机密且未授权）：「🔒 机密 · 向 JT 申请」，下附说明（已识别身份但不在名单 / 未识别登录身份）。
      2. 上传文件：绿色按钮「📎 文件」+ 原文件名。
      3. 网址：蓝色按钮「↗ 打开」（新窗口）。
      4. 暂无：有权限的人看到「填网址」「上传文件」两个按钮，其他人看到「暂无」。
      • 有权限的人在 2、3 旁还看到「修改」；所有者在机密项旁看到「已授权 n 人」。
    • 操作列：「编辑」（有权限时）、「授权」（所有者，仅机密文件）、「负责人（n）」（所有者，仅第二层文件夹）、「⋯」（有权限时）、「隐藏」（所有人，只影响自己）。
  • 默认折叠：每个人第一次打开时，编号含「.」且有子条目的文件夹全部折叠，即只展开顶层文件夹，显示到编号 n.n 这一层。「展开到第 2 层」按钮恢复的就是这个状态。

3.3 「⋯」菜单（openMenu() / doMenu()）

菜单项 出现条件 行为
新建子文件夹 / 新建文件 对象是文件夹 对话框：名称、说明；文件另有维护人、权限（团队内 / 工段 / 机密，默认团队内）。新条目放在末尾并展开父文件夹
上移 / 下移 不是第一个 / 最后一个 与相邻兄弟交换 order
升一级 不在顶层 移到祖父下、紧跟原父文件夹之后；非所有者不能移出本部门
降一级 上方紧邻的兄弟是文件夹 放进该文件夹末尾并展开它
移动到… 总是 对话框选目标文件夹（不能选自己与自己的子孙；非所有者只能选自己有权的文件夹）与位置（末尾 / 开头）
复制 总是 复制整棵子树（新 uid），根副本名称加「（副本）」，放在原条目之后
删除… 总是 见 3.5

非所有者对自己无权编辑、但有权新建的条目（自己部门的部门文件夹本身），菜单只有「新建子文件夹 / 新建文件」。

3.4 编辑与入口

  • 编辑（data-edit）：对话框字段：名称、说明、类型（仅无子条目时可改：文件 / 文件夹）、维护人（文件）/ 负责人（文件夹）、权限（团队内 / 工段 / 机密 / —）、自建列；所有者编辑顶层文件夹时多一个「可见范围」：所有能打开本页的人 / 仅 JT 可见。入口不在这里改。
  • 填网址：入口为空时；须以 http(s):// 开头，否则提示。
  • 修改入口（二次确认）：选「新的网址 / 上传一个文件替换 / 清空入口」→ 再弹确认框显示「原：… 新：…」，确认后才生效。网址与上传文件互斥，设一个就清另一个。
  • 上传：选择文件 → 存入文件库 → 写 asset、assetName，清空 url。

3.5 删除与回收站

  • 删除文件或空文件夹：确认后 trashed=true，记 trashedAt、trashedFrom。
  • 删除有子条目的文件夹：选择「保留子项，上移一级」（子条目移到被删文件夹原来的位置，依次排在它原来的位置上）或「连同子项一起删除」（只标记该文件夹，子孙随之不可见）。
  • 回收站（所有者）：按删除时间倒序列出；「恢复」回到 trashedFrom（若原父已不存在或也在回收站，则恢复到顶层），放在末尾；「彻底删除」删除该条目及其全部子孙记录。

3.6 拖拽移动（pointerdown/move/up，鼠标与触屏通用）

  • 只有所有者、且无搜索无筛选时出现拖拽柄。
  • 拖动时显示浮动标签「移动：编号 名称」，被拖行半透明；靠近窗口上下 60px 自动滚动。
  • 落点判定：目标是文件夹时，行高的上 28% = 放到它前面，下 28% = 放到它后面，中间 = 放进去；目标是文件时，上半 = 前面，下半 = 后面。落点行显示上沿线 / 下沿线 / 底色。
  • 不能拖到自己或自己的子孙上；落点违反「第二层只放文件夹」时弹提示且不移动。

3.7 撤销

  • 每次改动（新建、编辑、移动、复制、删除、恢复、彻底删除、改入口、上传、授权、负责人、增删列）都压入撤销栈，最多 300 步；按钮显示步数，悬停显示上一步名称。
  • 「↶ 撤销」或 Ctrl / ⌘ + Z（对话框打开时、或焦点在输入框时不触发）。撤销 = 把受影响的条目恢复为改动前的完整记录（新建的则删除）。
  • 撤销栈只在本人本次打开页面期间有效。目标设计下撤销本身也是一次改动，须走第 4.2 节流程或由部署者回滚（见 4.2）。

3.8 其他

  • 列管理（所有者）：「＋ 列」新增文本列；自建列可删除；所有人可隐藏任何列（只影响自己）。
  • 导出 JSON（所有者）：导出 {exportedAt, cols, items:[…附 number]}，文件名 文件索引_YYYY-MM-DD.json。
  • 人员选择器（「授权」「负责人」）：列出已选的人（显示姓名，可移除）；输入框按姓名搜索用户目录，同时列出打开过本页的成员；输入 6 位以上时可「按 ID 添加」。
  • 页脚说明：拖拽规则、编号规则、删除与回收站、入口三种状态、机密与「仅 JT 可见」的含义、「隐藏」只影响自己。原文见 reference_index.html 的 <footer>。

4 · 权限

4.1 现状（Claude 平台上的实现）

角色 现状能做什么
所有者（JT） 全部操作
部门负责人（平台「编辑者」，且在某个第二层文件夹的 leaders 里） 在本部门文件夹内部编辑、改入口、上传、新建、移动、复制、删除、撤销；不能改部门文件夹本身、不能移出本部门、不能拖拽
其他编辑者 只读
查看者 只读

机密入口：所有者、viewers 名单里的人、该部门的负责人能看到；其他人看到「🔒 机密 · 向 JT 申请」。

现状的漏洞，迁移时必须修正：机密入口与 ownerOnly 文件夹只是在浏览器里不显示，数据本身仍完整下发到每个能打开页面的人；部门负责人的编辑范围也只在页面上限制，平台层面任何「编辑者」都能写全部数据。新系统必须在服务端按第 4.2 节过滤与校验：看不到的条目与入口根本不下发，越权的写入直接拒绝。

4.2 目标设计：读、写、批、部署四权分开（《G-Choco Quant 运营机制》A11）

四种权限

权限 含义
读（Read） 看到条目与入口
写（Write）＝提议 提交一个「变更请求」（新增、修改、移动、删除、改入口、上传、改权限……），写明理由；提议不改变线上数据
批（Approve） 批准或退回变更请求，写明意见；批准不等于生效
部署（Deploy） 把已批准的变更请求应用到线上数据，并写入改动记录

角色与作用域

角色 读 写（提议） 批 部署
所有者（JT） 全部，含 ownerOnly 全部 全部 全部
部署者（JT 指定，可以是 Claude 或服务账号） 全部（不含 ownerOnly，除非另授权） — — 已批准的请求
部门负责人（第二层文件夹的 leaders） 全部非 ownerOnly 条目；本部门机密入口 本部门文件夹内部 本部门文件夹内部的、他人提出的请求 —
成员（团队内） 全部非 ownerOnly 条目；机密入口仅限 viewers 授权 任意位置（提议本身无害） — —
外部查看者 按授权 — — —

谁批（按变更作用的范围）

变更 批准人
某部门文件夹内部的新增、修改、移动、复制、删除、改入口、上传 该部门负责人；无负责人时为所有者
涉及第一层（中心级）或第二层（部门文件夹本身）的任何变更；跨部门移动 所有者
改权限相关字段：access、viewers、leaders、ownerOnly 所有者
列结构（增删列） 所有者
从回收站彻底删除 所有者

规则

  1. 不批自己的提议。批准人本人发起的变更，视为「提议 + 批准」合一，仍生成变更请求与改动记录；部署仍由部署者执行。
  2. 每个变更请求一条记录：id, 提议人, 提议时间, 类型, 目标 uid, 改前快照, 改后快照, 理由, 状态, 批准人, 批准时间, 批准意见, 部署人, 部署时间。状态机：草稿 → 待批准 → 已批准 → 已部署；分支 待批准 → 已退回、待批准 → 已撤回（提议人自己）。
  3. 部署时校验：目标条目自提议以来未被改过（比对改前快照或版本号）；若已被改过，变更请求退回「待批准」并提示冲突。部署后重排受影响的父条目，再写改动记录。
  4. 一次操作可能牵动多条（如删除文件夹并上移子项、复制子树、拖拽导致重排），一个变更请求包含全部受影响条目，原子部署。
  5. 改动记录（审计日志）只增不改，所有人可读；包括被退回与撤回的请求。
  6. 撤销 = 回滚：部署者可以对某条改动记录执行「回滚」，生成一个反向变更请求，按同样流程（回滚由所有者批准）。
  7. 服务端强制：读权限过滤在服务端完成（机密入口、ownerOnly 子树不下发给无权者）；每个写入接口校验角色与作用域。
  8. 个人浏览偏好（折叠、隐藏行列、筛选）不属于变更，不走流程，只存本人。
  9. 数字类改动一律记入《决策记录》——《文件索引》本身没有数字类内容，此条留作通用。

界面上需要新增的

  • 每个可编辑动作（新建、编辑、移动、拖拽、删除、改入口、上传、授权、负责人、增删列）提交后生成变更请求，界面上该条目显示「有 n 条变更待批准」，不立即改变树。
  • 「变更请求」面板：按状态分页（待批准 / 已批准待部署 / 已退回 / 已部署），显示改前改后对比、理由、提议人；批准人看到「批准 / 退回（须填意见）」；部署者看到「部署」。
  • 「改动记录」面板：时间、条目、改了什么、提议人、批准人、部署人；所有者与部署者可「回滚」。

5 · 迁移步骤

  1. 建库：按 2.1–2.4 建表；uid 原样保留（所有引用都靠它）。
  2. 导入 items.json 的 items 数组：去掉附加字段 number、depth、path 后入库（这三项由系统按 2.6 计算）。
  3. 账号映射：按 people_map.json 把 leaders、viewers、seen 中的平台 ID 换成新系统的用户 ID；所有者（JT）直接设为超级管理员。owner 字段是人名文本，按名字映射为用户 ID。
  4. 上传文件：把 assets/ 里的文件放进对象存储，更新对应条目的 asset。
  5. 入口网址：现有 url 多为 claude.ai 页面链接。文件迁移到新服务器后，由各文件维护人按第 4.2 节流程把入口改为新地址；在此之前保留原值。
  6. 导入 meta.json 的列定义（注意保留「freq 不显示」的行为）。
  7. 计算编号，与 tree.csv 逐行比对编号、层级、父子关系，应 100% 一致。

7 · 已知问题与建议

  • 客户端隐藏不是权限：见 4.1 末，必须服务端强制。
  • 负责人目前只认第二层文件夹：中心级（第一层）没有负责人字段的编辑入口；owner 字段在第一层文件夹上只是文本。建议新系统让第一层也能设负责人（例如风控中心、数据与知识中台），作为该中心的批准人。
  • owner 是自由文本：迁移时改为用户引用，避免改名后对不上。
  • 资产孤儿：条目进回收站后，上传文件仍占空间；彻底删除时建议一并删除文件。
  • 自定义列的键名用时间戳生成，迁移时原样保留即可。
