## 1 · What it is

The File Index is the **catalog and the only entry point** for every document, tool, program, and web page in G-Choco Quant. It is also the only source of record for who is responsible for each part and who maintains each file (*G-Choco Quant Operating Mechanism* 0.5). It does not store file contents. It stores only: an item’s place in the tree, its name and description, its maintainer, its access label, and its entry (a URL or an uploaded file).

The page is a **tree table**: one row per item (folder or file), with an auto-generated number on the left. It can expand and collapse, search and filter, and move items by drag. People with edit permission can create, rename, move, delete, change an entry, and upload.

## 2 · Data model

### 2.1 Item `items` (one record per item; primary key `uid`)

| Field | Type | Meaning and rules |
|---|---|---|
| `uid` | string | Primary key. Never changes after it is created. Format is unrestricted (the current form is `u` + time + a random string). Number changes do not affect it |
| `parent` | string | `uid` of the parent item; `""` for a top-level item |
| `order` | number | Sort key among siblings. After every structural operation, **renumber** it to consecutive integers: top level 0, 1, 2…; other levels 1, 2, 3… (see 2.6). An insert may temporarily use ±0.5, 1e9, −1, and so on; renumbering then snaps it back to an integer |
| `kind` | `"folder"` / `"file"` | Type. **Anything with children is treated as a folder** (regardless of `kind`) |
| `name` | string | Name. Required |
| `desc` | string | Description |
| `owner` | string | For a file: maintainer. For a folder: lead. Currently a name string (for example `Eric`). **After migration, store a user-ID reference** and resolve it to a name for display |
| `access` | `"团队内"` / `"工段"` / `"机密"` / `"—"` / `""` | Access label. Stored values stay as these strings: team / section / confidential / em dash / empty. Folders do not display it. `机密` (confidential) hides the entry (section 4) |
| `freq` | string | Update frequency (for example “weekly” or “when it changes”). The current page **does not show it as a column** (the code filters it out), but the data is kept. Keep the field in the migration |
| `url` | string | Entry URL. Must start with `http://` or `https://`. Mutually exclusive with `asset` |
| `asset` | string | Asset ID of an uploaded file. Mutually exclusive with `url` |
| `assetName` | string | Original file name at upload time, used for display |
| `leaders` | string[] | **Meaningful only on second-level folders (number n.n):** user IDs of that department’s leads (edit authorization; see section 4) |
| `viewers` | string[] | **Meaningful only on files with `access=机密`:** user IDs separately authorized to see the entry |
| `ownerOnly` | boolean | **Meaningful only on top-level folders:** when `true`, that folder and all descendants are visible only to the Owner (JT) |
| `trashed` | boolean | In the trash |
| `trashedAt` | ISO time | Time it entered the trash |
| `trashedFrom` | string | Parent `uid` at the time it entered the trash, used for restore |
| `c<timestamp>` | string | Value of a user-created column (key names are in `meta.columns`). The current data has no user-created columns |

### 2.2 Metadata `meta`

- `columns.cols`: definitions and order of visible columns, `[{key,label}]`. The base columns are fixed as `name` Name / `desc` Description / `owner` Maintainer / `access` Access / `url` Entry. They cannot be deleted. User-created column keys look like `c1739...` and can be deleted.
- `schema.v`: data-structure version. Currently 3.

### 2.3 Visit record `seen`

The key is a user ID. The value is `{t: ISO time}`. Written when an editor (not the Owner) opens the page (updated only if more than 7 days have passed since the last write; viewers have no write permission, so the write fails silently). Purpose: the people picker lists “members who have opened this page,” covering external invited members that platform search cannot find. **After migration**, if the new system has a complete user directory, search that directory directly and this collection can be retired.

### 2.4 Uploaded files `assets`

They currently live in the Claude platform asset library and are fetched at `/_blob/<asset ID>`. Allowed types: `.pdf .png .jpg .jpeg .gif .webp .md .json .csv .txt`. There is currently 1 file (`b1063547…`, a PDF). The item it belongs to is already in the trash. On migration: store the file in object storage, change `asset` to the new file ID or path, and keep `assetName`.

### 2.5 Each person’s own view preferences (live only in that person’s browser, not in the database, and do not need approval)

| Key (localStorage) | Contents |
|---|---|
| `kb3_col` | Which folders are collapsed `{uid:true}` |
| `kb3_hc` | Hidden columns `[key]` |
| `kb3_hr` | Hidden rows `[uid]` |
| `kb3_flt` | Filter conditions for each column |
| `kb3_seeded` | Whether the “first-visit default collapse” has already run |

### 2.6 Derived rules (must match exactly)

1. **Children:** items whose `parent` equals this `uid`, that are not in the trash, and that (the current user is the Owner, or the item is not `ownerOnly`), sorted by `order` ascending, and by `name` lexicographically when `order` ties. (`kids()`)
2. **Numbers:** depth-first from the root. The top level starts at **0** (0, 1, 2…); every other level starts at **1** (`parentNumber.1`, `parentNumber.2`…). Numbers are **not stored**. They are computed from position on every render. (`computeNums()`)
3. **Is a folder:** has children, or `kind=folder`. (`isFolder()`)
4. **Is in use:** the item itself and every ancestor are not in the trash, and (for a non-owner) there is no `ownerOnly` ancestor. (`alive()`)
5. **Owning department folder:** walk up the parent chain and find the item whose parent is top-level. That is the second-level ancestor (number n.n). (`stageOf()`)
6. **The second level holds folders only:** refuse any operation that would place a file on the second level (its parent is top-level), and show: “The second level holds folders only: level n.n holds folders only. Put files at n.n.n or deeper. Create a folder here first, then put the file inside it.” This applies to create, move up one level, move down one level, move to, and drag. (`l2file()` / `L2MSG()`)
7. **Renumber:** after every structural operation, rewrite `order` of the children of each affected parent to consecutive integers (top level starts at 0, other levels start at 1). (`renorm()`)

## 3 · Page and interactions (item by item)

### 3.1 Page header

- Title “File Index”. Subtitle “G-Choco Quant · numbers and entries for all knowledge, tools, systems, standards, files, code, and programs”. After that, the connection status (connected / not connected / read failed). Non-owners also see “Your ID: …” (so the Owner can authorize by ID).
- Toolbar: search box (searches name, description, maintainer, and number); “Expand all”, “Collapse all”, “Expand to level 2”.
- The Owner also sees: “↶ Undo (n)”, “＋ Top-level folder”, “＋ Column”, “Trash (n)”, “Export JSON”. A department lead sees only “↶ Undo”.
- Status area: the current identity note, and the result of each save (“Saving…”, “✓ Moved · time”, “Failed to save n items: reason”).
- “Hidden” bar: lists columns and rows this person has hidden. Each can be restored, or “Restore all”.
- Count bar: with no filter, “N items · x files · y folders”. With a filter or search, “n matches / files a / folders b / library total …”.

### 3.2 Table

- Columns: number + columns in `meta.columns` that this person has not hidden + actions. The header sticks to the top. Each column header has “Hide”. User-created columns also have “Delete” (Owner only).
- The second header row is the **filter row**:
  - Number column: a “Clear filters” button (disabled when nothing is filtered).
  - Name column: a type dropdown (All / File / Folder) plus a text field “contains…”.
  - Description column and user-created columns: a text field “contains…” (case-insensitive).
  - Maintainer, Access, and Entry: a **multi-select popover**. Options are the distinct values of files currently in use, with counts. An empty value is shown as “(empty)”. Entry options are fixed as “URL / Uploaded file / None”, plus “Confidential” when a confidential item exists. The popover has “Clear this column”.
  - Rule: filters on Maintainer, Access, and Entry match files only. A folder does not count as a hit when any of those three columns is filtered. Every ancestor of a hit is also shown (translucent, meaning it is only there as the path).
- Rows:
  - Indent `12 + depth×18` pixels (depth is capped at 4 for indent). Top-level rows get a background, a bold larger name, and a color bar on the left. Second-level names are bold.
  - Number column: the Owner, and only when there is no search and no filter, sees a drag handle “⠿”; an expand / collapse arrow (a spacer is hidden when there are no children); a number badge.
  - Name column: 📁 or 📄 plus the name (search hits are highlighted); a folder is followed by its child count; an `ownerOnly` folder shows a red badge “JT only”.
  - Maintainer: a colored pill (Eric blue, Yui purple, CZ green, JT orange, others gray). Hovering this column on a folder shows the title “Lead”.
  - Access: a pill (confidential red, section yellow, team gray). Folders do not show it.
  - Entry (folders do not show it), four states:
    1. The current user cannot see it (confidential and not authorized): “🔒 Confidential · ask JT”, with a note underneath (identity recognized but not on the list / signed-in identity not recognized).
    2. Uploaded file: a green button “📎 File” plus the original file name.
    3. URL: a blue button “↗ Open” (new window).
    4. None: people with permission see two buttons, “Enter URL” and “Upload file”; everyone else sees “None”.
    - People with permission also see “Edit” next to states 2 and 3. The Owner sees “n people authorized” next to a confidential item.
  - Actions column: “Edit” (when permitted), “Authorize” (Owner, confidential files only), “Leads (n)” (Owner, second-level folders only), “⋯” (when permitted), “Hide” (everyone; affects only themselves).
- Default collapse: the first time each person opens the page, every folder whose number contains “.” and that has children is collapsed. That means only top-level folders are expanded, and the view shows down through level n.n. The “Expand to level 2” button restores exactly this state.

### 3.3 “⋯” menu (`openMenu()` / `doMenu()`)

| Menu item | When it appears | Behavior |
|---|---|---|
| New subfolder / New file | The target is a folder | Dialog: name, description. A file also has maintainer and access (team / section / confidential; default team). The new item goes at the end, and the parent folder is expanded |
| Move up / Move down | Not the first / not the last | Swap `order` with the adjacent sibling |
| Move up one level | Not at the top level | Move under the grandparent, immediately after the original parent folder. A non-owner cannot move it out of this department |
| Move down one level | The sibling immediately above is a folder | Place it at the end of that folder and expand the folder |
| Move to… | Always | Dialog to pick a target folder (cannot pick itself or its own descendants; a non-owner can pick only folders they are allowed to use) and a position (end / start) |
| Duplicate | Always | Duplicate the whole subtree (new `uid`s). The root copy’s name gets “ (copy)” appended, and it is placed after the original item |
| Delete… | Always | See 3.5 |

For an item a non-owner may not edit but may create under (the department folder of their own department), the menu contains only “New subfolder / New file”.

### 3.4 Edit and entry

- **Edit** (`data-edit`): dialog fields: name, description, type (changeable only when there are no children: file / folder), maintainer (file) / lead (folder), access (team / section / confidential / —), and user-created columns. When the Owner edits a **top-level folder**, there is one more field, “Visibility”: everyone who can open this page / JT only. The entry is not changed here.
- **Enter URL:** when the entry is empty. It must start with http(s)://, otherwise show a prompt.
- **Change entry** (second confirmation): choose “New URL / Replace with an uploaded file / Clear entry” → then a confirmation dialog showing “Was: … Now: …”. It takes effect only after confirmation. A URL and an uploaded file are mutually exclusive; setting one clears the other.
- **Upload:** choose a file → store it in the file library → write `asset` and `assetName`, and clear `url`.

### 3.5 Delete and trash

- Deleting a file or an empty folder: after confirmation, set `trashed=true` and record `trashedAt` and `trashedFrom`.
- Deleting a folder that has children: choose “Keep children and move them up one level” (children move to where the deleted folder was, in order, in its old position) or “Delete together with children” (mark only that folder; descendants become invisible with it).
- Trash (Owner): listed by deletion time, newest first. “Restore” returns it to `trashedFrom` (if the original parent no longer exists or is also in the trash, restore it to the top level), at the end. “Delete permanently” deletes that item and all of its descendant records.

### 3.6 Drag to move (`pointerdown/move/up`, mouse and touch)

- The drag handle appears only for the Owner, and only when there is no search and no filter.
- While dragging, show a floating label “Move: number name”. The dragged row is translucent. Coming within 60px of the top or bottom of the window auto-scrolls.
- Drop target: if the target is a folder, the top 28% of the row height means place it before, the bottom 28% means place it after, and the middle means place it inside. If the target is a file, the top half means before and the bottom half means after. The drop row shows a top line / bottom line / background.
- Cannot drop onto itself or its own descendants. If the drop would violate “the second level holds folders only”, show the prompt and do not move.

### 3.7 Undo

- Every change (create, edit, move, duplicate, delete, restore, permanent delete, change entry, upload, authorize, leads, add or delete a column) is pushed onto the undo stack, up to 300 steps. The button shows the step count. Hovering shows the name of the previous step.
- “↶ Undo” or Ctrl / ⌘ + Z (does not fire while a dialog is open, or while focus is in an input). Undo = restore each affected item to its full record from before the change (or delete it if it was created).
- The undo stack lasts only for this person’s current visit to the page. **Under the target design**, undo is itself a change and must go through the section 4.2 flow, or be rolled back by the deployer (see 4.2).

### 3.8 Other

- **Column management** (Owner): “＋ Column” adds a text column. User-created columns can be deleted. Anyone can hide any column (affects only themselves).
- **Export JSON** (Owner): export `{exportedAt, cols, items:[…with number]}`. File name `文件索引_YYYY-MM-DD.json`.
- **People picker** (“Authorize”, “Leads”): lists selected people (show the name; they can be removed). The input searches the user directory by name and also lists members who have opened this page. After 6 or more characters are entered, “Add by ID” is available.
- **Footer notes:** drag rules, numbering rules, delete and trash, the three entry states, the meaning of confidential and “JT only”, and that “Hide” affects only yourself. The original text is in the `<footer>` of `reference_index.html`.

## 4 · Permissions

### 4.1 Current state (implementation on the Claude platform)

| Role | What it can do today |
|---|---|
| Owner (JT) | Every operation |
| Department lead (a platform “editor” who is in `leaders` of some second-level folder) | Inside **that department folder**: edit, change entries, upload, create, move, duplicate, delete, and undo. Cannot change the department folder itself, cannot move items out of the department, and cannot drag |
| Other editors | Read only |
| Viewers | Read only |

Confidential entries: visible to the Owner, people on the `viewers` list, and that department’s leads. Everyone else sees “🔒 Confidential · ask JT”.

**A hole in the current system that the migration must fix:** confidential entries and `ownerOnly` folders **are only hidden in the browser**. The data itself is still sent in full to everyone who can open the page. A department lead’s edit scope is also limited only in the page. At the platform level, any “editor” can write all of the data. The new system must filter and check **on the server** according to section 4.2: items and entries the user cannot see are never sent, and an out-of-scope write is rejected outright.

### 4.2 Target design: read, write, approve, and deploy are four separate rights (*G-Choco Quant Operating Mechanism* A11)

**Four rights**

| Right | Meaning |
|---|---|
| Read | See the item and its entry |
| Write = propose | Submit a “change request” (create, modify, move, delete, change an entry, upload, change permissions, and so on) and state a reason. **A proposal does not change live data** |
| Approve | Approve or send back a change request, and state an opinion. **Approval does not make it live** |
| Deploy | Apply an approved change request to the live data, and write a change-log record |

**Roles and scope**

| Role | Read | Write (propose) | Approve | Deploy |
|---|---|---|---|---|
| Owner (JT) | Everything, including `ownerOnly` | Everything | Everything | Everything |
| Deployer (designated by JT; may be Claude or a service account) | Everything (excluding `ownerOnly`, unless separately authorized) | — | — | Approved requests |
| Department lead (`leaders` of a second-level folder) | Every non-`ownerOnly` item; confidential entries in this department | Inside this department folder | Requests **made by other people** inside this department folder | — |
| Member (team) | Every non-`ownerOnly` item; confidential entries only when authorized in `viewers` | Anywhere (a proposal itself is harmless) | — | — |
| External viewer | As authorized | — | — | — |

**Who approves (by the scope the change affects)**

| Change | Approver |
|---|---|
| Create, modify, move, duplicate, delete, change an entry, or upload inside a department folder | That department’s lead; the Owner when there is no lead |
| Any change that touches the first level (center level) or the second level (the department folder itself); a move across departments | Owner |
| Changing permission fields: `access`, `viewers`, `leaders`, `ownerOnly` | Owner |
| Column structure (add or delete a column) | Owner |
| Permanent delete from the trash | Owner |

**Rules**

1. **Do not approve your own proposal.** A change started by the approver themself counts as “propose + approve” in one step. It still creates a change request and a change-log record. Deploy is still done by the deployer.
2. **One record per change request:** `id, proposer, proposed at, type, target uid, before snapshot, after snapshot, reason, status, approver, approved at, approval note, deployer, deployed at`. State machine: `draft → pending approval → approved → deployed`. Branches: `pending approval → sent back`, `pending approval → withdrawn (by the proposer)`.
3. **Check at deploy time:** the target item has not been changed since the proposal (compare the before snapshot or a version number). If it has been changed, send the change request back to “pending approval” and report a conflict. After deploy, renumber the affected parents, then write the change-log record.
4. **One operation may touch many items** (for example deleting a folder and moving its children up, duplicating a subtree, or a drag that causes renumbering). One change request contains every affected item and is deployed **atomically**.
5. **The change log** (audit log) is append-only. Everyone can read it, including requests that were sent back or withdrawn.
6. **Undo = rollback.** The deployer can run “rollback” on a change-log record. That creates an inverse change request and follows the same flow (the Owner approves the rollback).
7. **Enforced on the server.** Read-permission filtering happens on the server (confidential entries and `ownerOnly` subtrees are not sent to people who lack the right). Every write endpoint checks role and scope.
8. **Personal view preferences** (collapse, hidden rows and columns, filters) are not changes. They do not go through the flow. They are stored only for that person.
9. **Numeric changes** are always recorded in the *Decision Log*. The File Index itself has no numeric content; this rule is kept as a general rule.

**What the interface needs to add**

- Every editable action (create, edit, move, drag, delete, change entry, upload, authorize, leads, add or delete a column) creates a change request when submitted. The item shows “n changes pending approval” and the tree does not change immediately.
- A “Change requests” panel: paged by status (pending approval / approved, waiting to deploy / sent back / deployed). It shows the before/after diff, the reason, and the proposer. An approver sees “Approve / Send back (a note is required)”. A deployer sees “Deploy”.
- A “Change log” panel: time, item, what changed, proposer, approver, deployer. The Owner and the deployer can “Roll back”.

## 5 · Migration steps

1. Create the database: tables for 2.1–2.4. Keep each `uid` as-is (every reference depends on it).
2. Import the `items` array from `items.json`: drop the extra fields `number`, `depth`, and `path` before storing (the system computes those three from 2.6).
3. Map accounts: using `people_map.json`, replace platform IDs in `leaders`, `viewers`, and `seen` with user IDs in the new system. Set the Owner (JT) directly as super-admin. The `owner` field is a name string; map it to a user ID by name.
4. Uploaded files: put the files in `assets/` into object storage and update `asset` on the matching items.
5. Entry URLs: existing `url` values are mostly claude.ai page links. After files move to the new server, each file’s maintainer changes the entry to the new address through the section 4.2 flow. Until then, keep the original value.
6. Import the column definitions from `meta.json` (keep the behavior that `freq` is not displayed).
7. Compute numbers and compare them with `tree.csv` line by line for number, depth, and parent-child relationship. They should match 100%.

## 7 · Known issues and recommendations

- **Hiding in the client is not a permission:** see the end of 4.1. It must be enforced on the server.
- **Leads are recognized only on second-level folders today:** the center level (first level) has no editor for a lead field. On a first-level folder, `owner` is only text. The new system should let the first level set leads as well (for example Risk Center, Data and Knowledge Platform) and use them as that center’s approvers.
- **`owner` is free text:** change it to a user reference during migration, so a rename does not break the link.
- **Orphan assets:** after an item enters the trash, the uploaded file still takes space. Permanent delete should delete the file as well.
- **Keys of custom columns** are generated from a timestamp. Keep them as-is during migration.
